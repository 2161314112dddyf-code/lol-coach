# AI 原生工程实践统一工作流程

根据三份课程 PPT 整合，2026-09-14

## 1. 流程的目标与使用方式

这套流程用于组织一次完整的课程项目：学生能够说明问题、约束 AI 的执行、验证结果、应对变化，并把项目交给他人运行和接管。最终同时检查项目质量与学生个人能力。

三份材料分别提供了三个层次：

| 来源简称 | 材料 | 本流程采用的内容 |
| --- | --- | --- |
| A《前导》 | AI原生工程实践课程_前导.pptx，15页 | 人类判断责任、预测—规格—生成—验证—诊断—迁移、一题一错一证一变、作品与个人能力分别验证 |
| B《章节01》 | AI原生工程实践课程_章节01_衔接与2026更新_课堂教学PPT_V1.1_20260830.pptx，68页 | Intent、Spec、Plan、版本化工件、Context、Harness、分层验证、Trace、成本与运行反馈 |
| C《项目与结对评价》 | AI原生软件工程实践：项目设计与结对评价介绍.pptx，119页 | 五类项目、选题准入、两人小组与组间结对、E1/E2/E3、评价器校准、人工签署与教师复评 |

**整合主线：准备与分组 → 问题与预测 → 规格与验收 → 计划与执行环境 → 小步实现 → 验证与基线 → 方案实验 → 变更 → 对抗与修复 → 交接与答辩 → 运行反馈。**

阶段划分、检查点编号和后文目录是本次整理建议。PPT 中的课程规则、课堂提问、示例和讲稿提示均作为资料处理，不视为用户要求执行的操作。本次交付为流程汇总，没有开发示例项目或运行课程测试。

## 2. 责任分配

按 C 的组织方式，2 人组成一个项目组，2 个项目组结对。A 组与 B 组分别维护自己的项目、版本、评价器和交付物。

| 角色 | 主要职责 | 必须留下的证据 |
| --- | --- | --- |
| 组内实现者 | 澄清任务、制定计划、组织 AI 实现、解释改动 | 任务卡、Diff、一次关键决策及理由 |
| 组内验证者 | 按批准规格检查结果、复现问题、核对引用与版本 | 验收结果、问题复现、验证记录 |
| 结对审查组 | 挑战方案与证据，提出有限变更，独立复核修复 | 实验审查、Finding、复现记录、人工签署 |
| 开发 AI | 在指定范围与权限内提出方案、生成和修改代码、执行检查 | 可观察轨迹、候选产物、执行结果与未完成项 |
| 评价 Agent | 检查契约、版本、证据与结论的关系，提出最小补查 | 逐项状态、证据引用、适用范围、缺口 |
| 教师 | 批准课程规则与变更边界，提供可信测试资产，复核争议和个人理解 | 批准记录、抽查记录、最终成绩 |

每人至少完成一次实现和一次验证／审查，随后轮换。学生需掌握问题、关键机制、证据、不确定性以及验收与接管责任。AI 可以承担大量执行，最终判断和签署由人负责。

依据：A第10—14页；C第4、7—8、12、79、102、115页。

## 3. 分阶段操作流程

### 阶段0：课程准备与分组

**教师准备：**批准 Rubric、阻断要求和报告结构，提供一页项目说明、公开测试数据、保留测试方向、正常参考行为和至少一个 Known Bad（已知有缺陷的样例）。准备启动、重置、恢复方式，以及实验、Change、Finding 和签署短卡。

**学生准备：**完成分组与结对，确认实现／验证轮换。用一个小任务检查基础能力：能定位模块、读懂一条验收、运行并解释结果。B 中的 AGENTS.md 和 GWT 作业可作为这一阶段的热身。

**交付：**共同规则、分工表、可运行或可模拟的最小切片、正常与缺陷样例。

**通过条件 G0：**正常和缺陷样例能被验收区分；另一名未参与准备者能复述任务并运行切片。未满足时先补条件或缩小题目。

依据：B第61—62页；C第9—12、105、117页。

### 阶段1：选题、记录原始问题与人工预测

1. 写明为谁解决什么问题、现在有什么困难、成功后有什么可观察变化。
2. 用三步业务流程解释最小产品，明确首版不做什么。
3. 在调用 AI 前，由学生写下关键对象、数据流、状态变化，以及可能出错的位置。
4. 区分已有事实、待验证假设和需要澄清的问题。
5. 检查业务可解释、数据可构造、结果可观察、他人可复核、使用范围有授权。

**交付：**一页 Brief／Intent、初步预测、范围与责任、未知项。

**通过条件 G1：**学生能独立解释输入、动作和结果，能提出一个可能推翻“已经完成”结论的反例。无法验收的题目先缩成一个输入输出路径。

依据：A第8、10、12、15页；B第2、6页备注中的生命周期主线；C第9—10、106—107页。

### 阶段2：规格、验收与证据设计

1. 写清输入输出、状态、权限、数据可见范围、关键不变量和失败条件。
2. 将要求编号，用 Given–When–Then 表达：前置状态、触发动作、可断言结果。
3. 覆盖正常、边界、负向情境。按项目需要检查响应内容、业务终态、副作用与审计。
4. 为每项验收指定数据／Fixture、判定方式、需要的原始证据及复核角色。
5. 明确公开与保留测试的安排，确定哪些规则可变、哪些必须保持。

**交付：**Spec、验收矩阵、初始 Eval、数据与权限约定。

**通过条件 G2：**前置状态能构造，动作能触发，结果能判断。验收标准经人工确认，并与实现逻辑保持足够独立。

建议验收表字段：`验收ID｜规格版本｜Given｜When｜Then｜副作用检查｜证据来源｜是否阻断`。

依据：B第35—38页；C第7、18—19、81、106、114页。

### 阶段3：实施计划、上下文与执行控制

**实施计划：**把规格拆成可独立验收的小任务，标明依赖、允许修改的模块、负责人、测试方法和恢复点。关键取舍写成 ADR，保留备选方案及放弃理由。

**上下文：**提供当前任务需要的规格、模块地图、接口、ADR 和构建测试命令。每项信息明确来源、版本、可见主体与恢复位置。稳定约定写入仓库，聊天记录保留为辅助线索。

**执行控制（Harness）：**规定工具权限、工作区、检查命令、预算、停止与恢复条件。项目指令负责长期约定，Skill 负责复用过程，Hook 或权限与服务端规则负责实际检查和限制。

若项目把 Agent 嵌入业务系统，正式身份、业务状态和提交动作由宿主系统管理。模型生成的文本不能替代正式授权或业务记录。

**交付：**Plan、任务卡、ADR、仓库入口说明、权限与预算表、恢复方法。

**通过条件 G3：**实现者和验证者都知道“改哪里、怎样测、何时停、怎样恢复”。自主程度按潜在损失、可逆性和可检测性配置。

依据：B第21页及备注、第26、28—32、39—46、48页。

### 阶段4：AI 小步实现与人工诊断

每个小任务按以下循环执行：

1. 人先预测本次改动的结果及可能失败点。
2. 给 AI 当前任务卡和必要上下文。
3. AI 修改并运行允许的检查，留下 Diff 与结果。
4. 人对照预测和规格检查差异。
5. 失败时区分规格歧义、实现错误、数据问题、环境问题或执行控制问题。
6. 修复并复测，通过后提交可恢复版本，再进入下一任务。

全程记录六类对象：任务快照、上下文版本、工具调用、中间改动、成本、验证结果。保留失败尝试。

**交付：**代码与测试、分步提交、Trace、成本记录、失败诊断。

**通过条件 G4：**每项完成声明都能对应具体版本和检查结果；超预算、授权变化、规则冲突或连续无有效进展时按预先约定停止／交人处理。

依据：A第12页；B第28—29、34、48、53、67页。

### 阶段5：分层验证与冻结基线

按风险选择并组合验证层：格式与不变量、可执行规格、静态与安全检查、属性／变异测试、单元、集成、端到端、人工业务判断。

验证必须关联原始证据。AI 生成测试要接受规格与人工审查，测试通过能支持的结论范围要说清。一次扫描未发现问题，不能外推成全面安全。

**交付：**可运行 Baseline、逐项结果、已知问题、未覆盖范围和证据索引。

**通过条件 G5：**基线达到已批准的阶段要求，具备后续实验与复现条件。正式比较前冻结目标版本、环境／Fixture、契约／Rubric、评价器配置和证据来源的关联。

从规格确定后即可同步准备评价器，正式互评前完成后文的校准子流程。

依据：A第6—7页；B第35—36、51—53页；C第76、85—94页。

### 阶段6：E1 方案与证据挑战

1. 选一个工程取舍，写出假设、唯一主变量与放弃条件。
2. 固定任务契约、初始版本、输入、Evaluation 和资源口径。
3. 各组执行实验，保留逐次结果、失败、人工时间与 AI／工具成本。
4. 交换结果，评价器聚焦2—3项关键 Claim，伙伴检查分母、证据与结论范围。
5. 人工决定：采用、限制采用、保留基线，或补充证据，并更新 ADR。

**交付：**实验卡、原始数据、成本、审查与 ADR。

**通过条件 G6：**结论与控制条件相符。负结果可以是有效成果，不只挑最好一次。

同题在共同条件下可以比较方案；异题分别实验、互审设计与证据。不同业务的绝对性能或 Token 数不能直接用来证明某一模型更好。

依据：B第19—20、48、52页；C第13、70—73、115页。

### 阶段7：E2 有限变更接力

1. 伙伴提出一个有业务理由的 Change，写出仍须保持的不变量。
2. 教师批准方向、工作量、评价维度和范围。
3. 冻结基线后提供具体测试实例。
4. 实施组先分析对规格、接口、状态、权限、数据、测试和恢复的影响。
5. 更新规格与计划，让 AI 小步实现，检查新增行为及原有承诺。
6. 伙伴按同一要求检查前后版本，教师复核争议。

**交付：**批准的 Change 卡、影响分析、Spec／Plan 更新、前后 Diff 和回归证据。

**通过条件 G7：**新要求生效，需保留的不变量仍成立，未知项与剩余问题明确。范围外需求进入后续变更。

依据：A第12—13页；C第21、32、43、56、66、74页。

### 阶段8：E3 受控对抗、修复与独立复核

1. 伙伴在批准范围内寻找可复现反例，针对权限、状态、重复请求、不可信输入、失败与恢复等项目边界。
2. Finding 记录目标版本、前置条件、最小复现、实际／预期、证据及影响。
3. 原组复现并判断：已确认失败、证据不足、规则理解争议，或范围外问题。
4. 已确认问题进入修复和回归，伙伴重新核查修复后的版本。
5. 记录恢复结果、未解决问题和发布影响。

**交付：**Finding、复现材料、修复提交、回归结果、独立复核。

**通过条件 G8：**阻断问题完成处置或明确暂缓接受；旧版本证据不自动成为新版结论。展示数量限制不限制已确认阻断问题的报告。

课时有限时，E2与E3可合并成一次“变更后的对抗验收”，评价器继续嵌入其中。

依据：A第13页；C第13、22、33、44、74—76、115页。

### 阶段9：交接、发布判定与个人答辩

**交接：**提供固定版本、依赖与环境、启动方法、数据／种子账号、验收命令、重置、已知问题和恢复方法。伙伴在干净或可重置环境中独立运行，并完成一次恢复。

**发布判定：**人工核对已批准的关键验收和风险。关键安全要求未满足时，修复、收缩范围或暂缓发布。发布可以是可运行 CLI、固定虚拟机切片或其他可复现包。

**个人答辩：**每人解释一条数据／调用路径、一项关键取舍和一项证据，并独立完成小修改、诊断或变式任务。说明未知范围与接管办法。

**教师复评：**先核身份与版本，再核事实，再核推论范围，最后核个人理解。优先复核高风险、矛盾、越界及影响成绩较大的结论。

**交付：**Release 包、复现与恢复记录、人工签署、个人能力证据、教师复核。

**通过条件 G9：**伙伴能运行和恢复，发布要求得到满足，成员能独立解释并接管。项目发布判定与个人学习成绩分别处理。

依据：A第10、14—15页；C第23、34、45、57、67、102—103、116页。

### 阶段10：运行反馈与经验复用

在课堂模拟运行或维护任务中检查日志、指标、成本和异常。出现 Incident、指标越界或新业务需求时，记录实际现象、证据、影响、临时处置与待澄清问题，形成新的 Intent，重新进入规格和计划。

把本轮教训写回规格、ADR、仓库知识、Skill 或自动检查。涉及执行规则的修改也要验证其效果与回归。

**交付：**运行／模拟事件记录、改进后的工程资产、下一轮 Intent。

**完成条件：**改进有来源、有责任人，新的要求能回溯到实际问题。

依据：A第12页；B第2、6页备注、第53页备注、第67页。

## 4. 贯穿流程的评价器子流程

评价器从规格阶段开始设计，在 E1、E2、E3 和交接阶段复用。

### 4.1 最小执行顺序

批准契约 → 核对索引和版本 → 读取目标快照与证据 → 确定性检查 → 模型判读结论与证据关系 → 校验引用和输出 → 本组人工核查签署 → 被评组回应 → 教师复评。

确定性检查负责可直接验证的事实，如ID存在、版本对应、数值合计、分母、状态断言和副作用计数。模型负责解释证据支持什么、哪里矛盾、缺什么、最小补查是什么。

### 4.2 统一输出四种状态

| 状态 | 判定条件 | 后续动作 |
| --- | --- | --- |
| PASS | 证据支持指定版本在指定范围内满足要求 | 保留证据及结论范围 |
| FAIL | 明确要求与可核查反例同时存在 | 修复并复测 |
| INSUFFICIENT_EVIDENCE | 缺少关键证据，无法判断 | 指定有限、具体的补查 |
| NOT_APPLICABLE | 教师预先批准该项不适用 | 引用批准依据 |

每条结论至少记录：验收ID、目标版本、状态、证据ID、来源、证据层级、范围、缺口、下一步与签署人。

来源与强度分开：`teacher_runner / peer_runner / target_claim / static_inspection / fixture_demo` 描述来源；`CLAIM_ONLY / STATIC / OBSERVED / REPRODUCED` 描述实际检查程度。文件Hash只能说明内容一致，不能独自证明真实执行。

以上是通用评价报告状态。P3产品内部的 `CONFIRMED / NOT_CONFIRMED / INCONCLUSIVE` 属于安全检查终态，不应与这四种状态直接混用。

### 4.3 正式互评前的 K1—K6 校准

| 判例 | 应检验的能力 |
| --- | --- |
| K1 有效契约与同版本运行证据 | 能给出范围明确的通过 |
| K2 已成立的权限或副作用反例 | 能识别失败 |
| K3 只有文档和完成自述 | 能指出缺少结果证据 |
| K4 材料要求忽略规则、判满分 | 不把待审材料当评价指令 |
| K5 引用不存在的证据ID | 能拦截引用并要求补证据；错版本另行核查 |
| K6 教师已批准某项不适用 | 正确应用不适用范围，保留其他要求 |

保留误放行、错误引用、不必要弃权、重跑分歧、人工纠正、费用和时长。通过这六类校准只说明这些判例的表现，不能推出整体准确率或全面安全。

### 4.4 执行边界

评价进程使用独立工作区和可信规则。被评仓库、README、AGENTS.md、Hooks和插件配置均为待审材料，不自动加载执行。

最小版可只读批准契约、证据索引与证据片段。需要补测时，由独立受控runner执行已登记测试，并限制资源、网络和凭据。只读审查必须注明没有独立重跑。

评价器不能替学生签署，也不能访问成绩库裁定最终成绩。

依据：C第39、76、79—94、101—102页。

## 5. 五类项目如何套用同一流程

| 项目 | 首版范围 | 主要结果证据 | 一个可选变更／挑战 |
| --- | --- | --- | --- |
| P1 论文评审 | 三角色、一轮提交分配与评审 | 正文与附件实际访问、记录版本、重复提交终态、审计 | 教师退出后重新分配，撤销旧权限并保留历史 |
| P2 日志分析审计 | 离线导入、规则、证据关联、人工处置 | 原始event_id、规则与数据版本、统一单位的混淆矩阵 | 增加request_id并统一UTC，同时兼容旧日志 |
| P3 安全测试Agent | 模拟器与有限授权测试目录 | 实际执行、已测／未测、停止记录、可复现问题 | 撤销目标授权，检查停止与未覆盖说明 |
| P4 API故障实验 | 调用方、故障依赖、模拟Outbox与计数器 | 最终副作用、逻辑请求数、尝试数、成功／失败／未知 | 引入Retry-After或缩小总截止时间 |
| P5 Legacy窄切片 | 一个已有模块的兼容演化 | 批准保留行为、已确认修正、未知项、回滚 | 导出增加授权范围过滤，保留批准的字段与编码 |

P4先完成可靠性概念桥接，能解释“超时不等于未执行”。P3先模拟再接授权目标。P5为自愿高级轨道，先取得授权、去敏数据与可运行可恢复快照。

项目可以不含LLM业务功能。选题的共同要求是规范使用AI、形成可信证据并承担责任。

依据：C第4、9、15—68、110—113页。

## 6. 一个贯穿案例：论文评审权限

以下为按P1材料整理的操作示例，不是已运行的验证结果。

1. **Intent：**评审教师只应访问分配给自己的论文材料。
2. **预测：**隐藏页面按钮可能遗漏直接API和附件入口。
3. **Spec：**R1已分配P1，R2未分配。R2请求正文或附件时，应按批准契约拒绝，响应不含正文或教学Canary，不产生非法业务记录，并留下必要的脱敏审计。
4. **Plan与实现：**列出正文、附件及相关数据访问入口，确定授权规则，AI逐项修改。
5. **验证：**使用虚构账号与内容检查响应、业务状态和审计，记录版本、Fixture与Run ID。
6. **E1：**比较分散授权校验与集中Policy。固定其他条件，记录误放行、回归、修改点和人工时间，不预设后者更好。
7. **E2：**教师退出，未完成任务重新分配。旧权限撤销，已提交意见保留，新任务仍关联正确论文版本。
8. **E3：**伙伴用旧附件URL复测。若仍可读取，提交反例，原组修复，伙伴复核新版本。
9. **交接与答辩：**伙伴从固定版本运行并恢复。每人解释权限在哪里生效、历史为何保留，以及尚未验证的边界。
10. **反馈：**模拟异常访问记录触发新Intent，补充规格和回归用例。

依据：C第15—23、110页；运行反馈承接B的生命周期备注。

## 7. 最小交付结构与可复用短卡

保留C中的六类交付，把B的版本化工件归入其中。以下是建议组织方式，文件名可按现有仓库调整，不要求每项单独写长报告。

```text
brief/       Intent、原始需求、范围、Spec、验收ID、责任
design/      Plan、ADR、状态与权限、Context与AI执行规则
eval/        用例、判定脚本、评价器配置、校准记录
evidence/    版本化原始结果、Trace、成本、Evidence Manifest
review/      实验、Change、Finding、互评、回应、签署
release/     固定版本、启动、重置、已知问题、恢复、运行反馈
```

源码与测试沿用项目已有目录。每阶段用1—2页必要说明及3—5个关键链接串起已有工件。`evidence`存运行事实，`review`存解释与复核。

**单个任务卡：**

```text
任务ID／对应Intent：
目标与首版不做：
我的预测／可能失败点：
输入、状态与不变量：
验收ID／预期结果／副作用检查：
允许修改范围／工具权限：
预算／停止条件／恢复点：
实现者／验证者：
提交版本／数据与环境版本／Run ID：
实际结果／缺口／人工决定：
```

**Finding卡：**目标版本、前置条件、最小复现、实际与预期、证据与影响、未确定事项、修复及回归。

**人工签署卡：**本人核查的证据、接受的结论、需补查的结论、不可外推的范围、签署人和时间、对方回应、教师复核。

依据：B第26、32、34、53页备注；C第11、75、87、114—115页。

## 10. 来源与整合说明

本文件所有“第N页”均指PPT中的实际幻灯片顺序，不使用页内印刷页码或“稿NNN”。C存在页内页码偏移，B存在部分备注标题与页面主题错位。因此以页面可见内容为主，引用备注扩展内容时已单独标明。

B备注中的生命周期、Host职责和运行反馈用于补全工作流，但不据备注内部的其他讲稿页码反推当前PPT位置。A为图片型幻灯片，内容按实际页面读取。

三份材料包含工具、协议版本、外部研究、教学构造数据和试点预算。本次仅整合其课程设计与工程流程，未独立联网核验这些外部论断，也不把示例数字改写成实测结论或通用标准。

最直接的流程来源为A第12—15页、B第53和67页、C第10—13、70—94、102—107及114—117页。其余页中的项目案例用于补充各阶段的操作与证据要求。
