# 项目交接说明

## 1. 项目目标

从一场 LoL 对局回放或其时序数据出发，为玩家做赛后决策复盘。系统需要理解当时可知局面，结合英雄与阵容的人类经验，对候选行动解释收益、代价、风险、执行条件和改选信号。

用户每次只提供一局，不等于系统只能从这一局从零学习：允许使用外部游戏资料、版本知识、可核验的行动实测和已有教练经验。
不把“预测最后胜负”“模仿高手动作”“评价未发生的替代决策”混为一谈。不用漂亮解释或任意分数冒充真实胜率贡献。

## 2. 已经确定的关键方向

### A. 先有游戏时空与行动基础，再分析本局
用户特别否定了“手工给几项局面加几条攻略就直接试模型”的过度简化。系统必须知道或能查询：地图尺度与坐标、可通行区域与墙体、实际路线、当前移动能力、刷野清线等动作耗时、完成后状态。不能默认 LLM 已经准确知道这些。
这些能力可通过数据与工具实现，不必全部写进语言模型参数。

### B. 英雄特性是行动纲领，且必须看队友
不能用自己的英雄标签独立决定计划。用户提出的例子：功能型/食草打野，帮助需要在前期建立优势的线上英雄，可能是合理的战略方向。
这不是所有片段必须抓人的固定答案。要继续区分抓人、反蹲、护推、保护回城、放弃与换区，并核对当时条件。
“通常值得帮谁”来自可靠经验；“此刻来不来得及、能不能做”来自状态和工具。

### C. 战略知识优先来自人类已积累的经验
采用教练、职业选手、专精玩家的复盘/指南和实测。保留出处、版本、英雄组合、条件、例外和分歧。
字幕只是素材的一部分：必须尽量对应作者看到的画面和游戏时刻。作者未说明的原因不让模型补成作者观点。
未知组合可做假设分析，但明确这不是已验证经验。

### D. 暂不以模型训练为前置
语言教练可以用云端大模型。先做数据和能力基础，之后验证“状态＋经验＋工具＋云端模型”。
之前讨论的 0.01B～0.05B、训练样本数和大规模盲评只是探索建议，不是需求或已经验证的指标。
现阶段不要启动本地大模型微调、离线强化学习或训练世界模型。

### E. 用决策时的信息，而不是结果倒推
全回放数据可以保存供事实核验，但决策视角必须截断未来并处理可见性。
保留敌人最后可见信息及其时间，不直接传入隐藏的真实坐标。
区分“当时可获得的信息”和“玩家本人是否注意到”；没有视角与问答不能凭轨迹断言心理。

## 3. 候选整体架构

版本化静态数据与地图 → 行动耗时/状态工具 → 人类经验检索 → 当时可知局面 → 云端模型比较行动 → 核验与报告。

需要分开的数据对象：
- 静态机制：英雄基础属性、技能、装备、地图资产及单位。
- 时序状态：game_time、位置、血蓝、装备、经验、可知技能、资源及历史事件。
- 行动估计：输入条件、时间区间、结束状态、假设、数据依据、误差。
- 人类经验：来源、版本范围、英雄关系、适用条件、建议、例外、审核。
- 模型输出：候选、推荐、机会成本、风险、未知信息及证据引用。

这只是结构方向，不要求首轮实现所有对象或搭大型框架。

## 4. 当前真实进度

目前完成的是需求讨论与资源线索收集；本交接没有任何经过验证的代码仓库。
未用目标版本真实验证 NGRID 或 ROFL 解析器，未证明连续全图轨迹、兵线和可见性已经可得。
LOLPT 的数据入口/许可和精度未打通。官方时间线、Live Client、Replay 控制和 LCU 不应混成万能接口。
曾生成可行性实验材料，但用户认为先要建立时空/行动基础。因此当前阶段以基础能力核验为先，不立即执行数百条大规模实验。
一个 B 站字幕提取尝试未成功，不能宣称已经获得主播完整逐字稿或可用经验库。

## 5. 尚未确定但不阻塞静态数据工作的事项

目标服务器（国服还是支持官方公共路由的服务器）；目标回放的版本；首批深度覆盖英雄；是否已有对应版本游戏资产；人工审核人；未来云端模型供应商。
先用显式版本的公开静态数据做实验，标注“开发样本”，不要把示例版本等同于最终目标版本。
示例英雄可选 Ivern，仅用于数据通路，不代表固定产品英雄。

## 6. 工作偏好

用户希望直接动手，少给抽象、冗长、层层扩展的任务清单。每轮只交付一个可运行小闭环。
可采用 Windows 友好命令。先检查已有环境，技术栈建议不是硬性要求。
不用先做网页和付费产品。第一轮的价值是明确“哪些资源真的能取到、哪些字段可靠、下一个缺口是什么”。
