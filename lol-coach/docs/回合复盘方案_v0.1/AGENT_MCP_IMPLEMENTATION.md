# 复盘 Agent 技术实施方案

2026-11-12 的实现使用 `scripts.run_review_agent`。实际启动参数、模型后端、工具和验收以[运行手册](../../README.md)与[实战自验](../../reports/round_agent_acceptance_20261112.md)为准。下文保留初版设计供追溯。

2026-11-07 · 设计规格，供开发与验收。产品判断依据见[回合分析设计](AGENT_MCP_REVIEW_DESIGN.md)。本文中新增的命令、模块和工具均为拟实现项。

## 首次交付长什么样

在项目目录运行一条命令，给定蓝方厄斐琉斯 5:00 的冻结输入和同局的检查点清单。宿主调用模型，允许它通过本地 MCP 查资料、核对候选行动，保存第一张卡，再用这张卡准备 5:20 的输入，输出第二张卡。玩家读两张中文卡即可。开发者另能查证每个建议用了哪些事实、哪条条件变了、哪次调用失败。

| 第一版选择 | 依据 |
| --- | --- |
| 一个 Python CLI 宿主、一个本地只读 MCP 服务、一个可替换的模型回调 | 现有解析、冻结帧、前卡绑定和答复校验都可复用。引入 MCP 的代码只处理工具调用边界。 |
| 每帧启动一个 stdio 子进程；同一帧所有查询复用该连接 | 两帧原型中，进程生命周期天然限定可查询的时刻。先测实际启动耗时，再决定是否需要长驻服务。 |
| 基于文件的私有运行目录，沿用现有 JSON 格式；前三步用离线材料开发 | 原件已有哈希，重现一次失败和比较两种传输都容易。首个独立模型适配器建议支持本机 Ollama，模型名称和上下文容量由运行配置指定。 |

拟定命令，路径相对于 `lol-coach/`。示例中的 `MODEL_TAG` 由运行者换成已部署的模型名。

```powershell
$case = 'data/private/offline_finish_20261101'
.venv/Scripts/python.exe scripts/run_review_agent.py `
  --seed-bundle data/private/reasoning/round007-t293/bundle.json `
  --seed-answer data/private/reasoning_sessions/round007-t293/answer.json `
  --ready "$case/ready_final/manifest.json" --at 300 320 `
  --backend ollama --model MODEL_TAG `
  --output data/private/reasoning_sessions/agent-first-run
```

该用例从已校验的 4:53 计划开始，取清单内 300、320 秒两份原始检查点。5:00 的历史答案只供固定轨迹验收；新模型运行时，5:20 用的是本次 5:00 的答案。后续整局入口按清单顺序执行，首帧可使用已有的独立分析模式。私有样例和公开 CI 的合成样例分别计数。

## 一次执行的时序和协议

1. **加载与冻结。** 宿主验证 manifest 与 bundle，调用既有帧检查逻辑，核对每条资料的 `content_sha256`；旧版直接内嵌经验描述的条目按 `lookup_reference` 的等值规则核对。本机独立指定的种子帧与种子答案记录文件哈希，复验时与先前保存的基线比对。绑定先前答案后，用规范化 JSON 计算输入指纹。样例使用现有的 `max_chars=250000` 作为前卡绑定上限，模型容量另查。
2. **限定工具范围。** 宿主通过固定程序名启动子进程，把当前投影的私有文件位置和预期哈希作为启动参数。投影含模型用的 frame、该帧可查的资料正文和绑定标识。服务校验摘要，发现工具后宿主检查名称和参数模式与本版一致。模型侧参数只含查询内容，库中存在但本帧未授权的 ID 与无效 ID 共用拒绝路径。stdout 专供协议，诊断写 stderr。
3. **请求模型。** 输入沿用 `messages/tools/response_schema` 三个键。保留 `{"tool_requests":[...]}` 或 `{"answer":{...}}` 的互斥封装；宿主按启用的工具集生成说明，替换原有只描述资料查询的固定文字。每批 1～5 个调用，整批先验参再执行；新模式沿用默认每帧 6 次模型响应、最多 1 次修订，把 10 次上限统一计入所有工具调用。资料读取计数另存，便于与旧结果比较。
4. **执行工具。** 调用 ID 在帧内唯一。将 MCP 结果还原成业务 JSON，再交给模型；对照时比较业务内容和哈希。资料内容标记为参考数据。返回的当前事实只能引用原帧 `f_…`，前卡的 `h_…` 只用于历史比较。工具结果保存在旁表，工具读取期间 frame 不变。
5. **接受卡片。** 增强模式要求本次答案引用已经检查的一组 2～3 个候选 ID。宿主在最终答复旁记录该组的签名、规则结论和对应选项；出现歧义或结构化动作与建议明确冲突时进入一次修订。通过后先原子写本帧产物，最后写完成清单，关闭服务，才开放下一帧。自然语言表述及战术合理性仍交给评阅。

模型后端复用 `generate(request)`。文件后端继续支持宿主人工或自动回应。无人值守适配器可用本地 Ollama 的 `POST /api/chat`，设 `stream=false`、要求 JSON，在消息中传当轮工具参数模式和答案契约；解析 `message.content` 后交给同一个校验器。该模式由 Agent 执行工具。记录模型标识、可取得的版本/摘要、上下文配置和服务报告的 token 用量。进入会话前按模型实际容量给完整输入、工具结果和输出留空间；超出时报告 `context_overflow`，回到冻结输入生成阶段调整有依据的投影。实测这两个原帧各约 8.6 万和 9.3 万个规范化 JSON 字符，容量检查要使用对应模型的 token 计数或可验证的保守上界。[Ollama 官方接口](https://docs.ollama.com/api/chat)

## 三个工具的最小契约

| 工具 | 模型参数 | 服务端选择、返回和边界 |
| --- | --- | --- |
| `get_reference` | 单个 `reference_id` | 严格沿用当前帧白名单及 `lookup_reference`；返回资料、类型和出处。批量由调用封装表达，保留旧查询结果格式。 |
| `inspect_situation` | `fact_ids`，1～8 个不同的本帧 ID | 从当前帧逐字取 `entity_id, field, value, temporal_scope, observed_at_seconds`，附已有的可用时间、年龄和单位。兵线组保留 `spatial_groups` 的各组计数与估计标记。未知值原样返回。首版用于按 ID 复查，模型开场仍读取现有冻结帧。 |
| `compare_actions` | 2～3 个带类型的候选，可选一个假定失效的条件 | 逐项返回 `id, verdict, checks, fact_refs, unmet, unknown` 与本帧标识。每项检查记录规则 ID、依赖的实体与证据，区分当前事实和假设分支。参数模式见[可机读契约](compare_actions.v1.schema.json)。 |

以下是 5:00 可以提交给 `compare_actions` 的完整参数。模型负责给不同动作分配 ID。进入服务后还须验证 ID 唯一、目标类型、当前帧可见范围及谓词主体。

```json
{
  "actions": [
    {"id":"A","kind":"attack_structure","target_id":"0x40000030","requires":[]},
    {"id":"B","kind":"regroup","requires":[{"kind":"exit_route_known","entity_id":"0x40000034"}]},
    {"id":"C","kind":"reassess","requires":[]}
  ]
}
```

对于 A，规则从当前帧检索同一塔最近有效的 `tower_health`，5:00 可引用 `f_a229df0296d55e7bccf4`，该塔 299.602 秒的观测值为零，返回 `ruled_out`。B 查询退路，区域或路径证据不够时返回 `conditional`，并列出待核条件。C 表示原地重新判断。它能给玩家留出观察机会，是否最佳仍取决于威胁。

**规则的实现顺序。** 由程序按动作类型补齐必需条件，例如攻塔必须检查目标、执行人，现场前压必须检查执行人。空的 `requires` 只表示没有模型提出的额外条件。实体身份绑定和同字段最新观测从帧中查；对相同时间相互冲突的记录返回未知。对本人生命只取当前允许的观测语义，检测到零血后撤销依赖继续现场输出的前提；单条历史击杀消息只作旁证，恢复后重评。对 `ally_cover` 需要对应队友与行动的直接依据，单个位置点或能力描述返回未知。组号只在一帧内有效，跨帧重算目标附近成员与关系。

每个条件输出“满足／与证据矛盾／未知”。存在已证实硬冲突时行动为 `ruled_out`；只有未知或待确认条件时为 `conditional`；其余为 `checks_passed`，含义限于本版覆盖的检查项。宿主按 `frame_id + 候选规范化内容 + 规则版本 + 假设条件` 绑定结果。给定 `withdrawn_condition` 时，服务在副本里撤去该前提，检查推荐的退路是否仍依赖它。假设结果单列，只用于检查条件变化后的退路。

**答复绑定规则。** 每次成功的真实条件比较，都替换本帧唯一的活动候选清单；假设查询只对这份清单做压力检查。其后答案的选项 ID 集合须与活动清单完全相同。宿主把清单摘要、规则版本、结构化动作/目标和最终答案摘要存入旁表。已排除的行动不能列为首选或退路；仍有未知前提的行动不能标为已具备条件。对撤去保护后仍要求该保护的退路发出校验错误。沿用原有单键 `answer` 封装，旧文件桥可处理。自然语言与动作类型是否完全一致属于另行评阅的项目，程序只为结构化部分作保证。

## 计算、缓存和后续扩展

首版 `compare_actions` 提供定性检查。第二步按 `同一观察方＋实体＋字段` 建前缀索引，保存事件顺序、可见性变化和有效时刻；每个候选登记所依赖的目标、队友、兵团和失效时限。依赖变化先局部重算，按帧与现有全量算法对照。全局重大事件、定时重评和未选帧抽样用于发现新机会。

第三步才接数值时间。动作表示为有向无环步骤图，串行步骤加区间，多个并行前提取完成时刻最大值。截止区间 `[d0,d1]` 减完成区间 `[c0,c1]` 得 `[d0−c1,d1−c0]`。缺实测、途经地图未绑定、速度中途变化都使对应项未知或失效。先在合成夹具验证算法，再按既有 T5/T6 决定哪些数值可进入实局。拟采纳的数值应在**冻结帧前**生成并写入 `frame.calculations`；本轮工具产生的新数值只能留审计或后续重新冻结的帧。现有答案四项时间预算接受 `null` 或非负二元区间；带符号余量另存计算记录。[计时准入](../ACTION_TIME_TEST_TASK.md)

静态资料缓存以“规范化内容摘要＋序列化版本”寻址，每次命中仍先校验当前帧授权。动态结果只按上述完整帧、规则与参数缓存；跨队伍、跨局、跨规则的缓存命中视为错误。若下一阶段引入精简模型输入，先验证公开事实、未知项和合法引用的可检索性，再测质量与成本。

## 故障、输出与重跑

每次运行在 `data/private/reasoning_sessions/<run>/` 新建目录。各帧使用 `<时刻>/<尝试号>/` 保存 `input.json`、`tool_calls.json`、`comparisons.json`、`answer.json`、`validation.json` 和 `card.md`；最后写 `completed.json`，绑定各产物哈希。复用现有 `atomic_json` 的无覆盖发布方式。完整模型请求/响应与本机路径留在私有目录。文件桥沿用现有三键请求和封装校验。[现有会话桥](../../lol_coach/file_model_bridge.py)

增强校验还应主动做一次退路检查。宿主从首选的已声明队友依赖中取出保护条件，调用同一纯函数，撤去该条件后检查退路。即使模型跳过假设查询，校验也会运行。凡涉及未编码的自由文本依赖，留在评阅记录里，供后续决定是否增加规则。

恢复按最后一个已提交的帧继续，先核输入、实现/规则版本、后端配置、上一答案摘要及全部产物哈希。同一输出目录由单一写者占用；新启动者遇占用退出。进程中断且遗留锁时，通过新的运行目录引用并复核已完成帧，原始失败保留。对只读工具超时可在同帧按同一调用指纹限次重试，重试记录实际次数；模型重复提交同一调用 ID 按现有规则拒绝。模型超时标记该次尝试结果未知，显式开始新尝试才再调模型。资料摘要不符、未来事实、帧串线或 MCP 握手不兼容时终止本次帧处理并留下稳定错误码。输出清单区分完成、工具失败、答案无效、预算耗尽及部分完成。

## 开工顺序与验收

| 切片 | 可执行交付 | 验收口径 |
| --- | --- | --- |
| M1 工具通路 | 抽取直接工具注册表，沿用旧同步 runner；实现本帧 MCP 投影、stdio 客户端/服务端和单元测试 | 同帧同参数资料内容与直接调用等价。测试跨帧、跨队、伪造 ID、混入未来时间、坏哈希及同批非法项。现有默认行为和旧文件桥回归通过；实际启动子进程完成一次发现、调用和关闭。 |
| M2 两帧可重放 | 接入 `inspect_situation`、`compare_actions` 和串行执行 CLI，编写公开合成夹具与私有样例测试 | 两帧固定输入与固定工具请求的业务结果可复现。零血旧塔被排除，后方 6 兵不可并入前方 3 兵，本人零血导致现场输出条件失效。撤掉队友保护后检出依赖同一保护的假退路。中断恢复、前卡损坏和非预期帧覆盖都有用例。 |
| M3 无人值守实跑 | 接一个真模型，在新目录运行上述 CLI | 实际调用模型，生成两张通过双重校验的卡，且 5:20 绑定本次 5:00 的有效答案。记录模型标识、工具次数、耗时、可得用量和失败。固定录制轨迹只验证工程重现，真模型允许不同可行结论。 |
| M4 评测再扩整局 | 同一模型、冻结输入、预算对照直接工具与 MCP，再单独对照是否启用候选检查/增量调度 | 传输先比一致性。战术盲评看是否可执行、是否借用未来、退路及队友条件；允许平手。调度评测同时抽选中和未选帧，按整局隔离，记录漏报及通知延迟。优化需同时报告调用、延迟、token 与质量变化。 |

开发的回归入口是项目目录的 `python -m pytest -q`。M1–M3 增加带可选 MCP 依赖的集成测试；普通环境跳过的项在带依赖的验证环境中必须实际运行。公开测试不引用本地游戏文件，私有实局复现另外报告。每个切片独立提交；出现回归时可从已有直接查询和文件会话入口复现，保留旧会话与失败记录。

**本次已核的基线。** 按示例种子路径取 293 秒数据，核对 300、320 两份原始输入的文件哈希，依次绑定已有的合法答案。重建的两个模型可见帧分别与 `answers_final/t300`、`answers_final/t320` 完全一致，前案答案摘要也相符。两帧分别有 101、102 项事实和各 17 项可读资料。既有答案均重新通过 `validate_decision`。两帧标识分别为 `frame_ed6e1329dd9a01eadf7a4f33`、`frame_b1872202ec2a7be948df6c08`。重建路径可令本地审计中的基帧记录不同，应保留各自出处。新模型若改变 300 秒答案，320 秒的帧标识随之变化是预期行为。
